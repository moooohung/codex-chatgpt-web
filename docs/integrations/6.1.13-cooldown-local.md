# 6.1.13 local cooldown scheduling repair, 2026-10-22

Base: f657f05 compactresume. Upstream submission, tool ACK, completion and account
authentication contracts, compaction checkpoints/backoff, and memory fixes remain.

The former 30-minute delay was a local default, not a time supplied by the shown
provider card. New untimed alerts use a 3-minute local retry check. Only a normal
subsequent request can test recovery; no automatic verification prompt or Retry
click is sent. Repeat actual rejections escalate per account to 5/10/30 minutes,
persist across restart, and reset after an hour without a rejection. Concurrent
reports do not renew local waits. Longer explicit provider waits remain floors.
Exact old factory notices with an untimed card plus the bridge's appended
30-minute default migrate once to the original detection time plus 3 minutes.
The original store is saved in a private content-addressed backup first. Provider
durations, different notices, future-dated observations and manual preferences
are preserved. Expired migrated entries remain available to legacy-disable cleanup.
A security rejection never replays
the blocked physical request on another account. Independent new requests retain
existing authenticated routing; this patch adds no account escape.

New pauses leave account configuration enabled preferences untouched. Legacy
bridge-owned disables recover after expiry even when a timer was missed; manually
disabled or removed accounts are not revived. Cleanup cannot clear a subsequent
provider/usage wait. A local auth-partition failure supplies no routing proof but
does not fail another independently verified partition's request.

Visible page-level alert classification excludes error cards belonging to earlier
conversation turns. Active/latest and global cards still fail the current request.
Launcher retry deadlines are validated and propagated back to the worker so the
Responses client and compaction journal see the same account-wide backoff.

Tests are offline DOM, clock, fake partition and localhost HTTP fixtures. They do
not prove that nyang is currently permitted to send, or that provider compaction
completed. No model prompt, account switch, cookie/token change or worker control
is part of verification. Package and install evidence is stored separately.
