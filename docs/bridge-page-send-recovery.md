# Browser memory and delivery recovery candidate

This change stages a replacement for version 6.1.4. Active bridge jobs must finish before installation. The installation plan identifies exactly seven files: CLI, browser helper and manifest in both installed runtime locations, plus `app.asar`. It verifies original and candidate hashes, saves seven original backups, checks that bridge processes are absent and preserves profiles, credentials, configuration and runtime files outside this list. The installation script defaults to read-only `Check` and requires an explicitly authorized idle window for `Install` or `Rollback`.

The source build is review evidence. The installable runtime is a surgical overlay of the currently installed files, preserving existing automatic continuations, model selectors, Native2 ABI and token/goal/report routes. Launcher ASAR metadata and the existing unpacked Linux runner remain intact. Do not install the superseded ASAR or use the complete modular patcher to recreate this candidate.

Send acceptance is observed concurrently with keyboard acknowledgement. Recovery uses the original baseline and submission identity. Another activation needs settled input plus positive evidence that no trusted Enter, form submit or owned conversation request occurred, the document and exact draft remain unchanged, and no new response, generation or approval is visible. Ambiguous acceptance is observed without resending. Three activations and three reconciliation checkpoints bound recovery; cancellation and structured adapter errors remain terminal. Receipt deduplication also retains failures.

The visible `Message delivery timed out. Please try again.` banner is scoped to the current response and its Retry control, excluding quoted assistant/user text. Once generation and tools stop and approvals are absent, at most three deduplicated short continuations reconcile completed results and continue unfinished work. They retain the original capability, model, effort and abort/deadline ownership. The original task and Retry button are not replayed. Compaction recovery remains fail-closed. Model-family selection errors capture the owned picker before cleanup and preserve the original failure; they do not establish that the requested family is unavailable.

Physical browser admission defaults to four FIFO slots while eight logical owners can remain registered. Finished saved `/c/` conversations may be parked on an empty page and restored in the same partition. Temporary chats and unknown URLs retain their documents. Memory transitions and leases are serialized. Renderer recycling on resume uses measured private memory and completed-turn thresholds. GPU disabling and hard JavaScript heap limits remain optional.

Further browser weight reduction should first test lazy creation of the primary ChatGPT view and launcher UI. A managed Chrome route can remove Electron shell overhead but still renders the ChatGPT document; no comparative saving is claimed. GPU and heap policies require matching workload measurements. Electron documents [background throttling](https://www.electronjs.org/docs/latest/api/web-contents), [process memory metrics](https://www.electronjs.org/docs/latest/api/app), [supported switches](https://www.electronjs.org/docs/latest/api/command-line-switches) and [performance practices](https://www.electronjs.org/docs/latest/tutorial/performance).

`CODEX_WEB_GPT_SEND_RECOVERY=0` and `CODEX_WEB_GPT_DELIVERY_RECOVERY=0` disable their respective new recovery paths. Memory settings are defined by `launcher/electron/browser-memory-policy.cjs`. Final inbox reports contain exact candidate hashes, commits, commands, logs, install/rollback commands and limitations. Offline HTML, synthetic memory fixtures and release smoke do not prove live ChatGPT recovery, game execution or learning readiness.
